# Обновления TextPilot через GitHub

Начиная с 0.0.6 приложение проверяет:
https://github.com/ventureb0y/textpilot/releases/latest/download/latest.json

GitHub Releases хранит NSIS-установщик, его подпись и latest.json.
Tauri Updater проверяет подпись перед установкой. Проверка запускается через
3,5 секунды после открытия приложения; вручную — в настройках.
Установка начинается после нажатия «Обновить сейчас».

## Настройка GitHub Actions

Репозиторий: https://github.com/ventureb0y/textpilot

В Settings → Secrets and variables → Actions добавить:

- TAURI_SIGNING_PRIVATE_KEY — содержимое существующего файла
  %USERPROFILE%\.tauri\textpilot.key (не путь).
- TAURI_SIGNING_PRIVATE_KEY_PASSWORD — пароль этого ключа.
  Для ключа без пароля секрет можно не задавать.

Не создавать новый ключ: публичный ключ уже встроен в 0.0.5.
Приватный ключ и пароль не добавлять в Git и не отправлять в чат.
GITHUB_TOKEN выдаётся workflow автоматически.

## Выпуск

1. Отправить исходники и .github/workflows/release.yml в GitHub.
2. Согласовать версию в package.json, src-tauri/tauri.conf.json,
   src-tauri/Cargo.toml и записи textpilot в src-tauri/Cargo.lock.
3. Выполнить ./scripts/check-release-version.ps1 -Tag v0.0.6.
4. Создать тег v0.0.6 и отправить его именно в GitHub.
5. Дождаться успешного Windows release в Actions. Workflow запускает Rust-тесты,
   проверку Svelte и сборку, затем создаёт черновик релиза.
6. Проверить наличие setup.exe, setup.exe.sig и latest.json.
7. Опубликовать черновик как обычный релиз и назначить Latest.

До публикации черновик недоступен установленным приложениям.
Не перезаписывать файлы опубликованной версии; исправление выпускается
под новым номером. Ручной запуск workflow также должен выполняться на теге.
Теги с дефисом создают prerelease и не предназначены для стабильного канала.

## Переход с GitVerse (0.0.5 → 0.0.6)

В установленной 0.0.5 зашит старый адрес:
https://ventureb0y.gitverse.site/textpilot/latest.json

Изменение конфигурации в исходниках не меняет уже установленное приложение.
Для автоматического перехода после публикации 0.0.6:

1. Скачать latest.json из опубликованного GitHub Release 0.0.6.
2. Опубликовать этот файл как site/latest.json на старых GitVerse Pages.
   Внутри должны остаться ссылки GitHub на файлы конкретного релиза 0.0.6
   и подпись именно этих файлов. Генератор Tauri Action создаёт их автоматически.
3. Проверить доступность старого адреса и файлов GitHub без авторизации.
4. Открыть установленную 0.0.5 и проверить обновления.

GitVerse в этом случае раздаёт только переходный JSON; установщик загружается
с GitHub. После установки 0.0.6 следующие проверки идут напрямую в GitHub.
Если доступа к старым Pages нет, установить 0.0.6 вручную один раз и проверить
автоматический переход 0.0.6 → 0.0.7 при следующем выпуске.

## Проверка полного цикла

- До обновления записать текущую версию и проверить несколько своих фраз,
  словарных записей и настроек.
- На старой версии дождаться предложения обновить либо нажать
  «Проверить обновления».
- Установить обновление; проверить завершение установки и перезапуск.
- Убедиться, что отображается новая версия и сохранились данные/настройки.
- Повторить проверку: должно появиться «Установлена актуальная версия».
- При отключённой сети ручная проверка должна показать понятную ошибку,
  а приложение должно продолжать работать.

Локальные проверки исходников не заменяют этот тест на установленной сборке.

## Ручная сборка и старые скрипты

./scripts/build-signed-update.ps1 собирает и подписывает установщик локально,
запрашивая пароль ключа без отображения. Он также создаёт подписанный ZIP,
который использовался для GitVerse. GitHub workflow публикует непосредственно
NSIS .exe и не требует ZIP.

./scripts/generate-update-manifest.ps1 можно использовать для ручного манифеста.
Для .exe передавать .exe.sig; для ZIP — .zip.sig. Подписи невзаимозаменяемы.
